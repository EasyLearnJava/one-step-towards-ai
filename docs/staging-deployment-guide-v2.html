API Guide · version 2

What are we building?

Version 1 put an HTML page on AWS. Version 2 adds a small Python API behind the same address, so the page can ask a server for an answer instead of only showing fixed text.

The API has exactly two routes and no AI model yet. It is a walking skeleton: the smallest version of the future RAG and agent app that already runs end to end on the real stack (Python, FastAPI, LangChain, Docker, AWS Lambda, CloudFront, GitHub). Later steps add capabilities to it instead of rebuilding it.

App architecture: serve and watch

What happens after everything is deployed: for every page view, every click on the button, and all the time in the background. Read the numbers in order.

Serve: one click on the button

  1. The browser opens https://d****.cloudfront.net. CloudFront fetches index.html and app.js from the private bucket (arrows 2 and 3) and sends them back with the security headers. The page appears.
  2. The visitor clicks Say hello to the API. app.js calls /api/hello on the same address (arrow 1 again), which the page's security policy allows (connect-src 'self').
  3. CloudFront sees the path starts with /api/ and sends it to the Lambda function URL, signed with its own AWS identity (arrow 4). It passes the visitor's headers on, except Host.
  4. Lambda checks the signature and its two permissions: only this CloudFront distribution may call. It starts the container if none is running (a "cold start", about a second or two), otherwise reuses a warm one.
  5. Inside the container, the Lambda Web Adapter turns the call into a normal HTTP request to uvicorn on port 8000. FastAPI runs hello(), which fills the LangChain template and returns JSON (arrow 5).
  6. CloudFront adds the security headers and returns the JSON (arrow 6). app.js shows the message with textContent. Nothing is cached, so every click reaches the API.
  7. Anyone calling the bucket's or the function's own URL directly gets 403: only CloudFront may read or call them.

Watch: health check and logs

  1. Route 53 health checkers load the page (not the API) over HTTPS every 30 seconds, through CloudFront like a visitor, and look for the title One Step At A Time.
  2. The result becomes the metric HealthCheckStatus: 1 healthy, 0 unhealthy.
  3. The CloudWatch alarm switches to ALARM when the value stays below 1 for 2 minutes, and back to OK when it recovers.
  4. Each change goes to SNS, which emails you: one email when the site breaks, one when it recovers.
  5. Separately, everything the API prints (uvicorn's request lines, Lambda's START, END and REPORT lines) lands in the API's log group, kept 14 days.
Not watched yet: the health check only looks at the page. If the API breaks while the page works, no alarm fires. The Deploy workflow checks the API after every release; an API alarm is a later step.

Why Docker

The problem Docker solves

Our code runs on your PC because your PC has Python 3.13, the packages and the venv. A Lambda function has none of that. Docker packs the code and everything it needs into one box, called an image, that runs the same everywhere.

Think of a lunchbox. Your PC is a kitchen: everything is there, so you can cook anywhere in it. AWS is an empty table. Docker packs the finished meal with its plate and fork, so whoever opens the box gets exactly the same meal.
Image and container. The image is the packed box (a file). A container is that box opened and running. One image can run as many containers as needed: Lambda starts one per busy request slot.

Five reasons we use it

#ReasonWhat goes wrong without Docker
1Same box everywhere. The image that passes the tests on GitHub is the exact image Lambda runs."Works on my PC" problems: a different Python or package version on the server.
2Built on Linux, for Linux. Lambda runs Linux. Some packages contain compiled code (for example pydantic-core, used by FastAPI), and the build installs the Linux version.Packages zipped on Windows carry Windows-compiled files that crash on Lambda.
3Room to grow. A Lambda image can be up to 10 GB.A zip upload is limited to 250 MB unpacked. RAG libraries in step 4 (embeddings, vector clients) can pass that.
4Locked versions. The Python base image and the adapter are pinned by digest, the packages by version.A rebuild next month could quietly pick up different software.
5Not tied to Lambda. The same image runs on your PC, on Lambda, and later on ECS Fargate or EC2 if Lambda's limits (15 minutes per request) are outgrown.Moving off Lambda would mean repackaging the app.

Options we did not pick

OptionWhy not
Zip file upload to Lambda250 MB limit; must be built on Linux anyway; does not run on Fargate or EC2.
Lambda layers for the packagesSame size limit, more moving parts, still Linux-only builds.
EC2 server with a venvYou patch and run a server all day; it bills every hour with no visitors.

What is inside our image built

An image is built in layers, bottom to top. Each line of the Dockerfile adds one.

# Dockerfile (shortened; the full file is in the project root)
FROM python:3.13-slim@sha256:7249d558...                      # base, pinned by digest
COPY --from=public.ecr.aws/awsguru/aws-lambda-adapter:1.1.0@sha256:17cfd08e... \
     /lambda-adapter /opt/extensions/lambda-adapter          # the adapter
ENV PORT=8000 AWS_LWA_READINESS_CHECK_PATH=/api/health
COPY app/requirements.txt app/requirements.txt
RUN pip install --no-cache-dir -r app/requirements.txt       # packages
COPY app/ app/                                               # our code
ARG APP_VERSION=local
ENV APP_VERSION=${APP_VERSION}                               # commit SHA for /api/health
USER nobody                                                  # not root
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

.dockerignore sends only the app/ folder to the build, so tests, docs, Terraform and .git never enter the image.

The Lambda Web Adapter

WHATA small program from AWS, copied into /opt/extensions in the image.
WHYLambda does not send normal web requests; it sends events. FastAPI only understands web requests. The adapter translates between the two.
RESULTThe app has no Lambda-specific code. The same uvicorn app.main:app runs on your PC and on Lambda.
  1. Lambda starts the container. The adapter starts with it, and uvicorn starts the app on port 8000.
  2. The adapter calls /api/health until it answers. Only then does Lambda send requests (readiness check).
  3. For each Lambda event, the adapter makes a normal HTTP request to 127.0.0.1:8000 and turns the reply back into a Lambda response.
  4. Outside Lambda (your PC, Fargate), the adapter stays idle and uvicorn answers directly.

Do you need Docker on your PC?

No. Day to day, you run the app straight from the venv. Docker is how the app is packaged for AWS, and GitHub can do that packaging (pieces 2.5 and 2.7).

@app.get("/api/hello")

Why the version in /api/health?

After a deploy, the workflow calls /api/health and checks that version equals the commit it just built. "status ok" alone cannot tell old code from new: a failed update or a still-warm old copy would also answer ok. On your PC there is no build, so it says local.

You'll see, at http://127.0.0.1:8001 (checked on 26 November 2026):

/api/health   {"status":"ok","version":"local"}     # the build argument
/api/hello    {"message":"Welcome to the agentic world! ..."}
/docs         404
id            uid=65534(nobody)                      # not root
python        Python 3.13.18
Zscaler on this PC. The first build failed with CERTIFICATE_VERIFY_FAILED in pip install. Zscaler inspects HTTPS and re-signs every site with its own root certificate. Windows trusts that root; the Linux container does not. The fix: a CA bundle (the public authorities plus the Zscaler root) at %USERPROFILE%\certs\zscaler-ca-bundle.pem, handed to the build as a secret. Only pip uses it, and it is not stored in the image. Without the secret the build works as normal, so GitHub needs nothing. Do not switch certificate checking off instead: that would also hide a real attack.

The api job, step by step

  1. Check out the code (actions/checkout v4.2.2) and set up Python 3.13 (actions/setup-python v7.1.0). Both are pinned by commit SHA, so a changed tag cannot change what runs.

Result (26 November 2026): the second "image only" run, for commit 9d044a6, pushed one plain image: Docker v2 manifest, about 65 MB, tagged with the full SHA, with no index or attestation beside it. The scan on push completed: 9 HIGH, 5 MEDIUM, 2 undefined findings, typical for packages in the Debian base image. What happened on the first run: the image for commit fb5a197 arrived, but as three ECR entries: a tagged image index, the real image (untagged, about 65 MB) and a small untagged attestation. GitHub's Docker builder adds a provenance attestation by default, which turns the push into an index. Lambda does not accept an index, and the keep-5 rule would count the parts separately. Fix: the workflow now builds with --provenance=false, which pushes one plain image. Run "image only" once more (steps below) after the fix is on main. The three old entries are harmless; the lifecycle rule removes them over time, or delete them in the console.

ResourceFileWhat it does

aws_cloudfront_distribution.site (changed)main.tfA second origin (the function URL, HTTPS only, TLS 1.2, signed) and an /api/* behavior: GET and HEAD only, caching off, visitor's headers and query string passed on except Host, same security headers as the page.

Why not pass the Host header: the function URL only answers requests addressed to its own host name (****.lambda-url.us-east-2.on.aws). If CloudFront passed on the visitor's host (d****.cloudfront.net), Lambda would reject the request and the signature would not match. The managed policy Managed-AllViewerExceptHostHeader passes everything else.

Same steps as the version 1 guide's teardown (pause deploys, terraform plan -destroy, review, apply), with one extra point:

ECR is handled: AWS will not delete a repository that still holds images, so the repository is marked force_delete = true (decided in 2.6). terraform destroy removes it with all its images, like the website bucket. The repository policy Lambda added by itself goes with it. Expect 25 destroyed, and terraform state list empty afterwards.

Rebuilding after a teardown: the order

A plain terraform apply into an empty account fails: the Lambda function starts from "the newest image in ECR", and a brand-new repository has none. The deploy role does not depend on the function (its policy builds the function's ARN from the name), so it can come first and let GitHub push the first image. Build it in this order:

  1. ECR and the deploy role only: terraform plan "-var-file=..\environments\staging\site.tfvars" "-target=aws_ecr_lifecycle_policy.api" "-target=aws_iam_role_policy.deploy" "-out=staging.tfplan", then terraform apply staging.tfplan. 5 to add: the website bucket, the repository, its lifecycle rule, the deploy role and its policy. Terraform warns that -target is for exceptional cases; this is one.
  2. GitHub: set API_ECR_REPOSITORY to the URL from aws ecr describe-repositories --repository-names one-step-staging-api --region us-east-2 --query "repositories[0].repositoryUri" --output text and check AWS_ROLE_ARN. Then run Deploy website with image only ticked. GitHub builds and pushes the first image; no Docker on your PC.
  3. Everything else: a normal terraform plan and apply: 20 to add. It builds the rest of the version 1 site, the function (from the image just pushed), the CloudFront route and the permissions.
  4. GitHub: update SITE_BUCKET, WEBSITE_URL, API_FUNCTION_NAME, API_REGION; confirm the new alert email; enable the Deploy workflow if it was disabled.
  5. Deploy (full run, image only not ticked). The site and the API are back.

429 "Too Many Requests" from ECR Public open: to understand laterGitHub

WHAT HAPPENEDOn 26 November 2026, the Checks run for commit 9d044a6 failed in the api job's docker build. Our code did not break: AWS's public registry refused to send the Lambda Web Adapter image.
WHYGitHub's machines download from public.ecr.aws without logging in. AWS limits anonymous downloads per IP address, and GitHub's machines share IP addresses with thousands of other projects.
FOR NOWRe-run the failed job (Actions › the run › Re-run failed jobs). A re-run usually gets another machine with another IP.

How to read it: the Python base image from Docker Hub loaded fine (DONE). Only the adapter image from public.ecr.aws was refused, on line 15 of the Dockerfile. The same Dockerfile had built fine twenty minutes earlier for fb5a197, in both Checks and Deploy, so the cause is outside our code.

"But GitHub already has AWS access. Why no login?"

Two reasons, and both are true at once.

1. The failure was in Checks, which never logs in to AWS, on purpose.

WorkflowLogs in to AWS?Why
Checks (failed here)No. No AWS step at all; its first comment says "It never contacts AWS".It runs on every push and every pull request. The repository is public, so anyone can open a pull request; giving those runs AWS credentials would let a stranger's code act in your account.
Deploy websiteYes, through OIDC, as the role one-step-staging-github-deploy.It only runs when you click Run, only from main, only in the staging environment.

2. Even Deploy's login does not cover it: these are two different registries.

Your private ECRECR Public (public.ecr.aws)
What is in itOur API imagesAWS's published Lambda Web Adapter image (the one that was refused)
Owned byYour account, in us-east-2AWS's public gallery, shared by everyone
Does Deploy log in?Yes: docker login to ****.dkr.ecr.us-east-2.amazonaws.comNo. That login only covers the private registry.
Permission neededecr:GetAuthorizationToken (the deploy role has it, from 2.6)ecr-public:GetAuthorizationToken and sts:GetServiceBearerToken, in us-east-1 (the deploy role does not have them)

So "GitHub has AWS access" means: Deploy may upload index.html and push to our one private repository, nothing more. That is least privilege, on purpose. Downloading the adapter from public.ecr.aws is anonymous in both workflows, so both can hit the shared-IP limit.
